# ORG-X

Evidence-based Organizational Change Auditor · HackAlem AI · трек 11 Казахтелеком.

**После реорганизации кто теперь владеет каждой функцией — и чем это доказано?**

AI proposes. Evidence proves. Human decides.

Локальное приложение сравнивает две версии документов, строит Organizational IR, показывает изменения подразделений, сопоставления функций и потенциальные риски. Каждый вывод открывает точный текст «до» и доказательства либо журнал поиска «после». Аудитор сохраняет решение с обоснованием отдельно от неизменяемого результата анализа.

## Запуск

Нужны Python 3.9+ (рекомендуется 3.12), Node.js 22+ и pnpm 9.15 (`npm install -g pnpm@9.15.0`, если ещё не установлен). Для установки зависимостей нужен интернет; основной аудит затем работает без сети и API-ключа.

```bash
cd /Users/admin/hack-001016ea-intent
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
pnpm --dir frontend install --frozen-lockfile
pnpm --dir frontend build
cp .env.example .env
.venv/bin/python -m uvicorn orgx.main:app --app-dir backend --host 127.0.0.1 --port 8000
```

На другой машине замените путь `cd` на путь к клону. Откройте http://127.0.0.1:8000. API: http://127.0.0.1:8000/docs. Приложение рассчитано на локальное использование одним аудитором; привязка к localhost обязательна, аутентификация для сетевого сервиса не реализована.

Для разработки запустите backend указанной командой и отдельно `pnpm --dir frontend dev`. Vite на порту 5173 проксирует `/api` на 8000.

## Исходники и демонстрация

Единственные бизнес-источники:

- `work/hackalem/kazakhtelecom/Внутренний_аудит_редакция_8_до.docx`
- `work/hackalem/kazakhtelecom/Внутренний_аудит_редакция_9_после.docx`
- `work/hackalem/docs/track_11.txt`

Исходные файлы присутствуют в локальной рабочей копии. Каталог `work/` исключён из Git вместе с загруженными текстами, SQLite и кэшами. На новом клоне скопируйте три исходника в эти пути либо загрузите две версии через интерфейс. Тесты реальных источников показывают `SKIPPED`, если файлов нет; это **не** успешная проверка truth set.

1. Нажмите «Открыть контрольную пару» или «Новый аудит» и загрузите документы.
2. Откройте «Подразделения»: ДНМ и ДККМ сохранены, ДИТААД и ДОА добавлены в перечень (§3.4 обеих редакций). Изменение ролей §5.3 показано отдельно. Не утверждается, что два департамента заменены четырьмя.
3. Откройте перенос взаимодействия с субъектами СВК: §5.4.4/а–б «до» → §5.3.3/а–б «после». Новый ответственный указан коллективно; единственный владелец не выдумывается.
4. Откройте потенциальный пробел права формировать группы контроля качества (§5.6.2 «до»), изучите поиск и контраргументы (§5.5.2 и §10.7 «после»). Это не вывод о потере контроля качества.
5. Сопоставьте добавленное участие в органах управления (§4.4 «после») с ограничением управленческих решений (§5.8.1/в). Меры независимости и раскрытия совмещения включены в контраргументы. Доказанный конфликт не заявляется.
6. Во вкладке «Решение аудитора» укажите автора и обоснование. Проверьте журнал. В «Заключении» скачайте канонический JSON.

Точная разметка, исходные цитаты и SHA-256 приведены в `truth/source_truth.json` (22 случая). Это ручная авторская сверка источников при разработке, а не независимая экспертная приёмка: `human_signoff` остаётся `null`. Runtime не читает truth set.

## Реализованная доказательная политика

- Тождество текста + явно указанный ответственный + модальность + родительский контекст позволяют `PRESERVED`.
- Лексическое сходство создаёт кандидатов. Даже 100% совпадение текста не подтверждает передачу при смене контекста или конкурирующих владельцах.
- `MOVED` в контрольной паре выдаётся отдельным прозрачным правилом, проверяющим точные контексты взаимодействия с субъектами СВК и заголовки владельцев. Правило не обращается к truth set и не привязано к хэшу демофайла.
- `POTENTIAL_GAP` указывает потенциальный пробел явного полномочия, подкреплённый полным поиском и альтернативными основаниями. Отсутствие лексического кандидата само по себе оставляет `REQUIRES_HUMAN_REVIEW`.
- Для потенциального дублирования нужны разные явно названные владельцы и совпадающие обязанности в сопоставимом контексте. Общие обязанности, относительная зона ответственности и частичное совпадение направляются на проверку.
- Конфликт полномочий — потенциальный риск с контраргументами, не обвинение и не юридическое заключение.
- Каждый finding проходит проверку существования ссылок и наличия обеих сторон доказательной цепочки. Все системные выводы имеют `review_status=PENDING`.

## Проверки

```bash
.venv/bin/python -m pytest -q
pnpm --dir frontend build
.venv/bin/python scripts/benchmark.py
```

Тесты проверяют точность цитат, исходные хэши, ручные ожидания, семь запрещённых утверждений, воспроизводимость record, Word/PDF/Excel ingestion, загрузку и ошибки API, кэш, персистентность решений и неизменность JSON после human review. Adversarial-набор включает разные функции с похожим текстом, перефразирование, широкую функцию и несколько узких, частичное пересечение, отсутствие владельца, конкурирующих владельцев, сужение scope и смену права на запрет. Адаптер AI проверяется поддельным Responses-клиентом без платного вызова.

## Опциональный Responses API

В `.env` установите `ORGX_ENABLE_OPENAI=1`, `OPENAI_API_KEY` и `OPENAI_MODEL` (доступный вашему аккаунту snapshot). API-ключ никогда не передаётся в frontend. Кнопка AI явно предупреждает, что выбранные фрагменты IR будут переданы в OpenAI. При `0` внешних запросов нет.

Один ограниченный пакет содержит до 48 неоднозначных исходных функций и их кандидатов. Ответ — строгая JSON Schema с ID пар. Неизвестные ID, пары вне пакета, дополнительные поля, незавершённые ответы и ошибки приводят к детерминированному fallback. AI не может добавлять факты или менять типы выводов. Реализован формат `Responses.text.format` согласно [официальной документации Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

Ключ кэша включает полный запрос, schema, prompt version и модель. Сохраняются запрос, структурированный ответ, response ID и проверенные пары. Повтор воспроизводит сохранённый ответ. Новый сетевой ответ модели не считается детерминированным; канонический audit record вообще не зависит от него. `store=false` относится к параметру API и не является обещанием отсутствия обработки данных провайдером.

## Ограничения MVP

Автоматический структурный парсер обязанностей покрывает разделы 2 и 5 данного семейства положений. Остальные разделы сохраняются как точные searchable spans и используются доказательными правилами. Это не универсальная интерпретация любого документа и не гарантия обнаружения всех функций. Нераспознанная структура получает `REQUIRES_HUMAN_REVIEW`.

DOCX: основной текст и ячейки таблиц, без OCR, колонтитулов, сносок и вложенных файлов. Текст изменений Word не интерпретируется как принятая редакция. PDF: текстовые блоки с номером страницы, порядок чтения требует проверки; сканы без текста отклоняются. XLSX: значения и формулы как текст с координатой листа/ячейки; формулы не вычисляются. `.doc`, `.xls` не поддерживаются. Лимит файла 20 МБ, распакованного DOCX/XLSX 100 МБ, 12 000 фрагментов.

Штатные должности, правопреемство и фактические даты создания не выводятся из названий. Приложение с Кодексом этики упомянуто, но не предоставлено как самостоятельный источник. Внешние требования, бенчмаркинг операторов и рекомендации по перераспределению функций не входят в этот MVP.

Архитектура и API описаны в `docs/architecture.md`. Правила и human-signoff truth set — в `truth/README.md`.
